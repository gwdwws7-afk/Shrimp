# 项目级设计落地指南（Shrimp）

更新时间: 2026-03-24
适用对象: 策划、系统设计、关卡、战斗、QA、技术负责人

## 1. 文档目标

把方法论文档（00/01/02/03/04/20/24）转化为可执行、可验收、可追踪的项目设计流程。

## 2. 统一产出格式（每个系统必须具备）

每个系统设计文档至少包含以下字段：

- 设计对象
- 玩家核心幻想
- 30秒到3分钟核心循环
- 关键规则与约束
- 决策点与风险回报
- 反馈与可读性策略
- 学习曲线与失败学习点
- 核心参数区间（最小/推荐/最大）
- 验收标准（量化）
- 证据路径（测试/报表/录像）

## 3. 方法论对照轴（必填）

| 方法论 | 必填内容 | 判定问题 |
|--------|----------|----------|
| 00 总纲 | 幻想-循环-决策-反馈四段链路 | 玩家为什么会这样玩？ |
| 01 MDA | 机制 → 行为 → 体验因果链 | 规则是否真的导向目标体验？ |
| 02 FADT | 意图-可感知后果-可叙述过程 | 玩家是否看得懂“做了什么、为什么有效”？ |
| 03 Lenses | 至少 5 个关键问题 + 证据 | 当前方案最大的体验风险是什么？ |
| 04 Machinations | Source/Pool/Drain/Gate + 失控点 | 资源会崩盘或枯竭吗？ |
| 20 Boss（按需） | 身份、阶段、读招、反制窗口、失败学习点 | Boss 是否在“教与考”玩家？ |
| 24 群战（按需） | 三层敌人模型、据点节奏、爽压平衡 | 群战是否“压迫连续且可决策”？ |

> 说明: Boss 模块必须覆盖 20；群战/波次/敌人 AI 模块必须覆盖 24；经济/成长必须覆盖 04。

## 4. 评审打分标准（100 分）

| 维度 | 分值 | 通过线 |
|------|------|--------|
| 体验目标清晰度 | 20 | >= 14 |
| 机制-行为因果完整度 | 20 | >= 14 |
| 反馈可读性与教学 | 15 | >= 10 |
| 参数与经济可调性 | 15 | >= 10 |
| 验收与证据完备度 | 20 | >= 14 |
| 扩展性与复用性 | 10 | >= 7 |

判定规则:
- 单项低于通过线，模块状态不得标记为“可收口”。
- 总分 >= 80：可进入 P1 深化。
- 总分 70-79：允许开发推进，但必须附整改时限。
- 总分 < 70：仅允许做修订，不进入内容扩展阶段。

## 5. 评审流程（标准）

1. 目标对齐: 先确认该系统服务的幻想与体验目标。
2. 方法审查: 按 MDA + Lenses + 对应专项（Boss/群战/经济）评审。
3. 可执行化: 把“建议”落到参数、关卡脚本、资源需求或测试用例。
4. 门禁化: 把关键验收项接入现有 PlayMode/CSV/报告链路。
5. 复评: 每周更新完成度与风险。

## 6. 设计决策记录模板（DDR）

建议每个重要改动都记录一条 DDR：

- 背景
- 决策
- 影响模块
- 风险
- 回滚方案
- 验收证据

DDR 使用要求:
- 每个 P0/P1 设计变更必须绑定一个 `DDR-ID`。
- `TaskList` 的任务项需能追溯到 `DDR-ID`。
- 门禁失败修复需补一条“纠偏 DDR”。

## 7. 当前阶段优先级（与项目状态一致）

1. 关卡与流程内容深度
2. Boss内容化闭环
3. 技能/UI/音频资源化
4. Steam正式实接

## 8. 常见失配与修复方向

- 失配: 方法论正确，但无参数区间  
  修复: 增加“参数预算表 + 验收阈值”

- 失配: 设计评审有结论，但无落地责任人  
  修复: 每条结论补“owner + 截止时间 + 证据”

- 失配: 功能已做，体验未达标  
  修复: 把体验问题映射为可测指标（节奏、可读性、重复性）
